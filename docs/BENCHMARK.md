# Benchmark

Numbers below come from a live run of `scripts/eval_heldout.py` (fixed seed
20261030) on the synthetic evaluation set — every label ships in the repo
(`cases/ground_truth.json`, `data/synthetic/closed_cases_history.csv`) and all
data is regenerable via `scripts/make_synthetic_data.py`. No third-party data.

Run date: 2026-10-23 · Pipeline commit: Phase-6 eval build · Eval n = 20 case-pack cases
(28 labeled closed-case history rows stratified at the same seed).

## A. Deterministic engine fidelity (20/20 cases)

| Metric | Result |
|---|---|
| Verdict accuracy vs ground truth | **100% (20/20)** |
| Pattern accuracy vs ground truth  | **100% (20/20)** |

Cases in a human-in-the-loop pause still carry their provisional verdict and
pattern recorded at pause time; both matched ground truth.

## B. Risk-threshold-only baseline

Labeling each case "fraud" when the trigger `risk_score ≥ threshold`
(no graph evidence, no LLM):

| Threshold | 0.30–0.55 | 0.60 | 0.65 | 0.70–0.75 |
|---|---|---|---|---|
| F1 | 0.857 | 0.938 | 0.968 | **1.000** |

Caveat (stated honestly): the synthetic case pack is separable by risk score
by construction, so a threshold sweep hits F1 1.00 at 0.70. This baseline
produces **no pattern label and no evidence trail** — it cannot explain
*which* fraud family (card-not-present, ATO, card testing, …) or why. The
pattern classification story is the engine's, not this baseline's.

## C. Plain-LLM-no-graph baseline (ablation: what the graph adds)

One Nemotron 3 Nano prompt per case, given a flat 12-transaction history of
the card and explicitly forbidden from using graph/device-sharing/prior-case
context:

| Metric | Result |
|---|---|
| Verdict accuracy | **0.25 (5/20)** |
| Fraud recall | **0/15** — it answers "legitimate" on every fraud case |

A bare LLM looking at a flat transaction list sees one slightly odd
authorization among twelve mundane ones and calls the card fine. The same
trigger, once contextualized by the TigerGraph evidence (device sharing
across customers, connected confirmed-fraud cases, velocity across the
card graph), yields the 100% fidelity in section A. This is the central
ablation of the submission: **graph-structured evidence, not model
capability, is what resolves these cases.**

Reproduce: `python scripts/eval_heldout.py` (needs `NEBIUS_API_KEY` for
section C; `--skip-llm` runs A/B/D/E without any API call).

## D. Propose/decide separation (model ≠ decision-maker)

Nemotron proposes a pattern; the deterministic policy engine (rules R1–R10)
decides. Across the 20-case run:

| Outcome | Count |
|---|---|
| Cases completed and evaluated | 9 |
| Model proposal matched engine pattern | 6 |
| Engine overruled the model proposal (recorded with reason) | 3 |
| Agreement rate (completed cases) | 66.7% |
| Cases paused in human-in-the-loop awaiting analyst evidence | 11 |

The 11 paused cases proceed through the same `_attach_model_proposals` step
when their pending evidence request is submitted; they are counted
separately rather than dropped silently.

## Known limitations (same honesty bar as the README)

1. All labels are synthetic and generated by the same scripts that generate
   the evidence — accuracy figures measure *pipeline self-consistency on the
   published pack*, not real-world performance.
2. Fraud recall of the plain-LLM baseline (section C) uses one minimal
   prompt with no tool use; a heavier budget could improve it, but that is
   exactly the graph-evidence trade this project uses tools for.
3. Section A counts provisional verdicts for human-in-the-loop pauses.
4. Human-in-the-loop cases (11/20) are unresolved by design in a single
   benchmark pass; the API exposes their pending evidence requests.
